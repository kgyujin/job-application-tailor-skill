# 페르소나 검토

서류를 새로 쓰거나 크게 고친 뒤, 분석 보고서를 마무리하기 전에 읽는다. 같은 글을 서로 다른
독자의 눈으로 다시 읽어 한 번의 자기 검토로는 놓치는 문제를 찾는다.

## 페르소나

| 페르소나 | 보는 것 | 주로 쓰는 단계 |
|---|---|---|
| 채용 담당자 | 30초 안에 필수 요건 충족이 보이는가, 회사명과 직무명이 맞는가, 문항에 답했는가, 분량과 형식, 상투 표현 | A의 이력서와 자기소개서 |
| 현업 면접관 | 직무 역량의 깊이, 기술적 판단의 이유, 과장으로 읽히는 표현, 면접에서 파고들 지점 | A의 자기소개서와 포트폴리오, C |
| 사실 검증자 | 원본과 사용자 확인 내용 대조, 수치와 기간, 역할 동사, 팀 성과와 개인 성과 구분, 공개 범위 | 모든 산출물 |
| 교정 편집자 | `style-guide.md`의 윤문, 반복, 동의어, 가운뎃점, 맞춤법과 띄어쓰기 | 모든 제출용 산출물 |
| 기업 분석가 | 출처의 신뢰도와 날짜, 사업 구조 이해, 자료 사이의 충돌, 추정과 사실의 구분 | D, E, F |
| 커리어 코치 | 공고 핵심 요구 2~3개와 소재 배분, 문항 사이 소재 중복, 다른 지원자와 다른 점 | A의 작성 전 설계, F |

## 실행 규모

- 새 자기소개서나 여러 서류를 함께 쓴 경우: 해당 단계의 페르소나를 모두 적용한다.
- 문장 몇 개를 고친 작은 수정: 사실 검증자와 교정 편집자만 적용한다.
- 분석 모드(D, E, F): 기업 분석가와 사실 검증자를 적용하고, 결과를 서류에 연결했거나 F라면 커리어 코치를 더한다.

## 실행 방법

- 서브에이전트를 쓸 수 있는 환경(Claude Code의 Agent 도구, Codex의 협업 에이전트)이면 검토
  페르소나를 병렬로 실행한다. 각 검토자에게는 검토할 산출물, 근거 자료 경로, 공고 요약, 해당
  페르소나의 점검 항목만 넘긴다. 검토자는 수정하지 않고 지적만 돌려준다.
- 쓸 수 없으면 페르소나마다 따로 한 번씩 읽는다. 한 번 읽으면서 여러 관점을 섞지 않는다.
- 검토자 의견을 반영한 뒤 `scripts/check_text.py`를 다시 실행한다.

## 의견이 충돌할 때

1. 사실 검증자의 지적이 가장 앞선다. 사실과 공개 범위를 해치는 제안은 반영하지 않는다.
2. 다음은 채용 담당자, 현업 면접관, 기업 분석가이고, 그다음은 교정 편집자, 마지막이 커리어 코치다.
3. 새로운 사실이 있어야 반영할 수 있는 제안(예: "성과 수치를 넣으면 좋다")은 고치지 않고
   사용자에게 묻는 질문으로 바꾼다.

## 기록

검토 메모에 아래 표를 남긴다. 반영하지 않은 지적도 이유와 함께 적는다.

| 페르소나 | 지적 | 조치(반영, 보류, 질문) |
|---|---|---|

현업 면접관이 찾은 "면접에서 파고들 지점"은 검토 메모에 남겨 사용자가 설명을 준비할 수 있게 한다.
설명할 수 있다는 것이 사실 확인을 대신하지는 않는다.
